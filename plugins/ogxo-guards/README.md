# ogxo-guards

Pattern-based hooks for sensitive git staging, generated file paths, and large Write content or added patch text. Supports Claude Code, Grok Build, and native Codex tool payloads. Requires jq; the limits below apply.

## Install

```bash
claude plugin marketplace add ogxo-io/plugins
claude plugin install ogxo-guards@ogxo
```

## What each hook does

All three are `PreToolUse` hooks. A match exits with code 2 and reports the reason to the host. Claude Code and Grok Build use `hooks/hooks.json`; the explicit Codex manifest exports `hooks/codex-hooks.json`. Codex hooks must be enabled and the plugin trusted in the host settings. Codex maps `exec_command` to the `Bash` matcher and native `apply_patch` to `Edit|Write`; the scripts read the native payloads as well as Claude payloads. In Codex, file-protection and large-file-guard also run on the `Bash` matcher, for the heredoc `apply_patch` form that Codex intercepts from `exec_command` and applies as a patch (`apply_patch <<'EOF'` or `applypatch <<EOF` with the patch as the heredoc, optionally after `cd <dir> &&`). They read a command that starts with that form, allowing assignment words such as `LC_ALL=C` and backslash-newline continuations in the prefix, and check the patch lines after its first line (`hooks/patch-files.jq:49-53`, `hooks/codex-hooks.json:33`); any other command gives them no paths and an added size of 0.

- **env-file-guard** (matcher `Bash`): for each `git add` or `git stage` in the command (including `git -C <dir> add`), it checks only the pathspecs given to that subcommand, not the rest of the command line, so `cp .env ../wt && git add src/a.rs` passes. A pathspec whose name is sensitive is rejected. For a broad add (`-A`, `--all`, `-u`, `.`, a directory, or a glob), it runs `git status --porcelain --untracked-files=all` on those pathspecs and rejects the add if any listed path is sensitive; gitignored files are not listed, so they don't trigger it, and `-u` looks at tracked files only.
  - Sensitive by default (matched on the file name): `.env` and `.env.*` except `.env.example`, `.env.sample`, `.env.template`, and `.env.dist`; `*.pem`, `*.key`, `*.p12`, `*.pfx`; `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519` (not their `.pub`); any name containing `credentials` or `.secret`.
  - Per repository: add patterns to `.claude/ogxo-guards-sensitive`, one extended regular expression per line matched against the path (`#` starts a comment), for example `(^|/)\.npmrc$` or `(^|/)\.envrc$`. Neither is in the defaults because both are often committed without secrets.
  - It does not see `git commit -a`, adds run through `xargs`, `$(...)`, scripts or aliases, or quoting it can't split on spaces. Keep secrets in `.gitignore`.
- **file-protection** (matcher `Edit|Write`; also `Bash` in Codex): compares normalized paths against `node_modules/`, `vendor/`, `.git/`, and lock files (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lockb`, `Cargo.lock`, `go.sum`, `Gemfile.lock`, `poetry.lock`, `uv.lock`). For native `apply_patch` and the heredoc `apply_patch` form in Codex, it checks Add, Update, Delete, and both Move endpoints, resolving heredoc paths against the `cd` directory when there is one (`hooks/patch-files.jq:22-36`, `hooks/patch-files.jq:54-62`, `hooks/file-guard.sh:17`). Codex does not pass `exec_command`'s `workdir` to hooks: an intercepted heredoc patch is applied in that `workdir` (Codex 0.160.1 source, `codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs:193-200` and `:372`), the hook payload carries only `command` (`exec_command.rs:521-524`), and the hook `cwd` is the turn's working directory (`codex-rs/core/src/hook_runtime.rs:200` and `:248-253`). Heredoc paths are therefore resolved against the turn's working directory, so the `node_modules/`, `vendor/`, and `.git/` checks miss a heredoc patch whose `workdir` puts it under one of them; lock-file names are still matched. It reads patch lines the way the Codex 0.160.1 apply_patch parser does (`codex-rs/apply-patch/src/streaming_parser.rs`; `hooks/patch-files.jq:16-42`): a trailing carriage return is removed (`:143`); at the top level and after an Add or Delete section, a header matches after trimming surrounding whitespace, Unicode spaces included (`:176`); inside an Update section only trailing whitespace is trimmed (`:227-229`), so a line there that starts with a space is a context line, not a header (`:318`); and `*** Move to:` sets the destination only before the first hunk line and only once (`:253-256`). Where Codex rejects the whole patch instead (`:351-367`), as for a tab-indented header inside an Update section or a second `*** Move to:`, the hook still matches the line after a full trim and checks the path it names (`hooks/patch-files.jq:21-36`). Any other shell command (`cp`, `rm`, `sed -i`, `npm install`, a script, or `apply_patch` in any other shell form) can still change these files, and path checks do not resolve symlinks. Build output such as `dist/`, `build/`, or `generated/` is not matched, and other lock files (`composer.lock`, `Pipfile.lock`, `gradle.lockfile`) are not in the list.
- **large-file-guard** (`Write` in Claude/Grok; `Edit|Write` and the heredoc `apply_patch` form on `Bash` in Codex): compares Write content, or the added patch text per file, against 1,048,576 characters (`hooks/file-guard.sh:29`). Patch counts include the newline on each added line and count Unicode characters, not bytes. Update counts exclude existing content and removed lines, so this does not impose a limit on final file size. Added text in several sections of one path is summed; separate paths in one patch are counted separately.

## Requirements

`jq` on `PATH`. Without it each hook prints a notice and does nothing (it never rejects a call it could not read).

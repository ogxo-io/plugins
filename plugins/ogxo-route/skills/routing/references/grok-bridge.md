# Running grok through its bridge

Read from Step 3 of the routing skill before the first bridge call in a
session. `<plugin-root>` is ogxo-route's own folder, which the routing skill
gives; `<data>` and `<path>` below are grok-build's, as this file explains.

To run grok, call its bridge from Bash rather than dispatching the `grok-build:grok-delegate` agent: in auto mode the agent's nested write can be denied by the permission check. Find the script with `ls -d "${CLAUDE_CONFIG_DIR:-$HOME/.claude}"/plugins/cache/*/grok-build/*/scripts/grok-bridge.mjs | tail -1`, then run `CLAUDE_PLUGIN_DATA=<data> node <path>/grok-bridge.mjs run --background --write --fresh "<brief>"` from the directory the task works in (`--write` is required; without it grok runs read-only and leaves only a patch). `<data>` is grok-build's own data folder, `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/data/grok-build-<marketplace>`, where `<marketplace>` is the folder after `plugins/cache/` in the bridge's path (`xai-grok-build` for xAI's own marketplace). Set it on every bridge call (`run`, `runs`, `show`, `stop`): the bridge records its runs in whatever folder `CLAUDE_PLUGIN_DATA` names, and the shell can carry another plugin's, so without it `/grok-build:runs` does not list the run. Follow up with `show <run-id>`, and `run --background --write --resume-last` for a fix round. A large fix round, or one after a long run, starts `--fresh` instead, with the original brief, the fix list, and the diff so far: a resumed session carries its whole history, and long ones have died partway through a round. The user can still ask for the agent or `/grok-build:delegate` by name.

While a grok run is in flight:
- **Check that it is moving, not only whether it ended.** A wait loop that only checks for completion waits out a hung run until its time limit. Get the run's Grok session id from `CLAUDE_PLUGIN_DATA=<data> node <path>/grok-bridge.mjs runs <job-id>` (the "Grok session ID" line, or the session column of the table), then run `bash "<plugin-root>/scripts/grok-progress.sh" <session id>`. It reports `working`, `idle` (the turn ended: fetch the result with `show`), or `stalled` (a turn is open and nothing was written for 10 minutes). On `stalled`, stop the run with `CLAUDE_PLUGIN_DATA=<data> node <path>/grok-bridge.mjs stop <job-id>`, restore the files it touched, and dispatch it again with the same brief.
- **Never type into a running bridge session.** `grok -r <session id>` loads the saved history but not the live output of the bridge's headless process, so a busy run looks idle there, and a message typed into it starts a second agent in the same session and working tree, editing alongside the first. To watch a run, use `runs`, `grok-progress.sh`, or `tail -f` on the session's `updates.jsonl`. `grok-progress.sh` with no argument lists every grok session running on the machine (from any Claude session) with its state, its folder, and the start of its brief. Join with `grok -r` only after `grok-progress.sh` says idle, or after `stop`. Tell the user the same when they ask how to look at a grok run.
